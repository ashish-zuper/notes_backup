## Dev log

### API-5667 — QXO order polling: promotion, cancellation and dispatch fixes

*Repo:* `master_service`, `scheduler_service` · *Branch:* `API-5667` · *Ticket:* [API-5667 — Master Service: Create a Polling system for qxo orders](https://linear.app/zuperinc/issue/API-5667/master-service-create-a-polling-system-for-qxo-orders) · *Commits:* `0df25eafc` `2c7f893` `a8103d453` `020dc82a7` `f46410eec`

- Purchase orders sent to QXO now actually advance. Polling was running on schedule but every order stayed at "sent to vendor": the supplier's order detail was never translated into the shape the shared status pipeline reads, and the status vocabulary had no mapping for QXO's own values. Orders sent to SRS and ABC Supply were unaffected throughout.
- Fixed a case where an order that moved through two supplier statuses inside one polling interval would leave the purchase order stuck indefinitely. The poller now brings the order status up to date first and applies the delivery update on the following pass.
- Supplier-side cancellations were never detected. QXO returns that message under a different field name than its other errors, and the code only read one of them — so the whole cancellation path was dead. Fixing the reader also restores real error text on every other QXO call, which previously fell back to a generic "request was unsuccessful". A cancelled order now reads "Order Voided by QXO" on the purchase order.
- Found and fixed a silent stall: the background sweep reported success while queueing nothing. A job that had stalled hours earlier left a record behind that swallowed every subsequent run for that supplier account, and the queue library gives no error when this happens. The sweep now verifies the job really was queued, clears the blocking record automatically, and tells apart a genuine overlap from a stale one. A related retention setting was being silently ignored in both services, so failed background jobs had been accumulating without limit.
- Line prices now reconcile against what the supplier actually billed, and the logs carry per-stage counts, timings and reasons so a poll that does nothing can be told apart from a poll that failed.
- Follow-up fix to the stall detection above: it checked whether a job was already running immediately after queueing it, but the queue hands work to an idle worker in the same instant — so it was describing the job it had just created. Every run logged a spurious 'already in progress, skipping' while the work actually went ahead. The check now happens before queueing, and a job still waiting to start counts as in-progress rather than being cleared away.
- Supplier invoices now land on the purchase order. An invoiced QXO order previously reached "invoiced" with no invoice number, no activity entry and no PDF, because the supplier does not return an invoice number alongside the order — it has to be looked up separately. The poller now resolves it before recording the invoice, and an order still moves to invoiced even if that lookup fails, so only the invoice detail is missing rather than the status.
- Fixed a crash affecting ABC Supply as well as QXO: the document-attach worker called a proof-of-delivery method that only SRS implements, so every delivery on the other two suppliers threw. Combined with the retention bug found earlier, those failures had been piling up in the job queue. It is now a logged skip.
- The supplier's invoice lookup requires a company number that appears on no order, so it is now read from the current-user endpoint and cached per connection the same way the profile id already was. The invoice number itself still has no documented field despite the download endpoint requiring one, so a lookup that cannot find it records the full response row for diagnosis rather than guessing at a value.
