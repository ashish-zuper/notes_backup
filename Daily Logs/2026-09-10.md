### API-5667 — Supplier order tracking: mark complete on the order, not an event

*Repo:* `master_service` · *Branch:* `API-5667` · *Ticket:* [API-5667 — Master Service: Create a Polling system for qxo orders](https://linear.app/zuperinc/issue/API-5667/master-service-create-a-polling-system-for-qxo-orders) · *Commits:* `f64a74f9a`

- Marking a supplier order complete in the external tracker used to work by finding that order's most recent event and flagging it, which meant writing an order-level fact onto an unrelated historical record and only working if an event happened to exist. It now calls the tracker's own order-status endpoint directly, keyed on the purchase order. Fewer calls, no race against an event arriving mid-update, and it works for QXO orders, which have no events at all because they are polled rather than pushed.
- The tracker reports success and a changed-row count in the response body separately from the HTTP status, so both are now checked. A call that succeeds but changes nothing almost certainly means the order was never registered with the tracker at submit, which previously looked identical to success.
- Known gap left in place: this runs as fire-and-forget from a request, so a transient network failure loses the completion signal permanently — the purchase order will not re-enter a terminal status to retrigger it. Making it durable means moving it onto a background job.
