## Dev log

### staging — S3 migration sort-memory & write-pool fixes
*Repo:* `workflow_builder_execution_curator` · *Branch:* `staging` · *Commits:* `f264938`

- Fixed the S3 migration worker crashing with MySQL "Out of sort memory": removed the `ORDER BY created_at` from the blob-fetch queries, which had been forcing a filesort that packed multi-MB JSON payloads into the sort buffer. Processing order doesn't matter for the drain, so the sort was pure cost.
- Stopped the worker repeatedly pausing on DB write-pool pressure. Workflow and node migrations now share a single concurrency budget, and the node path no longer nests its concurrency limiter per parent group (which had allowed up to concurrency² simultaneous writes and saturated the pool).
- Workflow and node migrations now run concurrently instead of one after the other — they touch different tables with no shared mutable state.
- Batched the database writes: stale rows collapse into one bulk `UPDATE`, and blob migrations commit in chunked transactions (one connection per chunk) with a per-row fallback. This holds far fewer write connections and raises the safe concurrency ceiling.
- Added a stuck-page safeguard: the worker now aborts with an alert after several consecutive batches make no progress, preventing an infinite reprocessing loop during an S3 or DB-write outage (the queries re-fetch from offset 0).
