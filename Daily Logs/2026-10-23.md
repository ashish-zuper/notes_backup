### API-6488 — Supplier import memory and crash recovery
*Repo:* `scheduler_service` · *Branch:* `api-6488-supplier-master-product-import-lower-memory-use-and-resume` · *Ticket:* [API-6488 — Supplier master product import: lower memory use and resume after a crash](https://linear.app/zuperinc/issue/API-6488/supplier-master-product-import-lower-memory-use-and-resume-after-a) · *Commits:* `33aa63b` `78a3836`

- A supplier whose import fails, a nightly start skipped because a run is still in progress, and an abandoned run now each alert by Slack and email instead of only showing in the summary or logs; a stuck run is treated as abandoned after 20 hours so it can no longer block the next night's start.
- The SRS import now downloads its catalog to a temp file, validates it, uploads the S3 backup straight from the file and processes 1,000 products at a time, instead of holding the whole catalog in memory and stringifying it again; on a 1 GB container the SRS peak fell from about 416 MB to 309 MB, and the old code is killed under a 370 MB cap where the new code completes.
- Temp catalog files use fixed names created exclusively, so a crashed run leaves at most one file and a planted symlink is never followed; QXO shares the same download helper.
- Opened PR #145 with full-import before/after results: identical data across all ~127k master products apart from SRS raw records, which are now written only on first insert.
