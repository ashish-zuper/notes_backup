### API-4899 — ABC order tracking correlates on transaction ref
*Repo:* `master_service` · *Branch:* `API-4899` · *Ticket:* [API-4899 — Update Platform DB entry for PO for ABC order creation](https://linear.app/zuperinc/issue/API-4899/update-platform-db-entry-for-po-for-abc-order-creation) · *Commits:* `dacb59445`

- ABC Supply purchase-order tracking now registers Zuper's own transaction reference (the request id we submit) with the platform order tracker instead of ABC's confirmation number, matching how SRS already works. ABC echoes this reference back on its order webhooks, so the platform can correlate inbound ABC events to the right Zuper PO.
- The ABC webhook parser now reads that reference off the event, enabling a stable transaction-ref path for resolving which PO an event belongs to. The confirmation-number path stays as a fallback, so pre-existing behaviour still works.
- Improved debug visibility for supplier webhooks: the resolution path that matched is logged when an event is enqueued, the confirmation reference is now included when a PO can't be resolved, and the order tracker logs the correlation key it registered.

### Execution curator — Slack alert refinement (design)
*Repo:* `workflow_builder_execution_curator` · *Branch:* `staging` · *Commits:* `02d9c62`

- Wrote and committed a design spec for cutting Slack alert noise from the background maintenance service. The plan collapses per-run start/summary messages and DB pause/resume pairs into a single daily digest per worker (one row per run, idle runs collapsed), delivered each morning at 09:00 IST, while errors, crashes, service lifecycle events, and manual-script progress keep firing immediately.
- Digest data accumulates in Redis and is emitted by a new daily cron worker (leader-elected across replicas). Formatting is unified on the monospace-table style already used by the backlog script, with a config kill-switch to fall back to the current immediate-alert behaviour.
