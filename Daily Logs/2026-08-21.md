## Dev log

### API-5553 — QXO catalog import
*Repo:* `scheduler_service` · *Branch:* `API-5553` · *Ticket:* [API-5553 — Scheduler Service : Import QXO Catalog](https://linear.app/zuperinc/issue/API-5553/scheduler-service-import-qxo-catalog) · *Commits:* `9198c96`

- Full QXO US catalog now imports as part of the nightly supplier master product job — 78k products / 159.5k variants, ~4.5 min end to end.
- Runs in three streaming phases (count variants per product → build availability index → rebuild and write each product as it completes). Counting first is what keeps it under pm2's 1000M restart limit; buffering the catalog instead peaks at 1.25 GB and would leave the agenda lock wedged for 17h.
- Archive entries are inflated straight out of the zip rather than extracted — ~55 MB of temp disk instead of ~984 MB.
- The dump ships no variant label, so option values are derived per product from the attributes that actually differ across its variants. Width/length read as one "W x L" token to match how QXO presents size; where labels still collide the item number is appended (5.7% of variants). Keyed on item number, not label, so relabelling never orphans a vendor catalog link.
- Availability is three-state upstream and never (false, false), so any edge means the branch can supply the variant. A run that doesn't cover the whole catalog skips retirement rather than mass-retiring products it never saw.
- Import logs peak RSS / heap / CPU against a budget, which is how we found the real issue: no `--max-old-space-size` is set anywhere, so V8's default ceiling sits *above* pm2's kill threshold and it hoards garbage. Capping the heap cuts measured peak ~40%. Deploy-side fix, not done yet.
- QXO price sync (`catalogSyncQxoProducts`) is still a stub, so imported products can't be priced yet. Needs the per-customer Keycloak refresh-token flow that master_service already implements — QXO's client is public, there's no client secret.
