## 3. Major-feature deep-dive

Side-by-side comparison of the eight load-bearing features. Each entry: how SRS does it today (with the in-repo reference) versus how ABC exposes it (with the doc anchor), then a one-line verdict.

### 3.1 Authentication & token lifecycle

| | SRS | ABC |
|---|---|---|
| Grant type | OAuth2 **client-credentials** (per app) | OAuth2 **authorization-code + refresh-token** (per tenant); 3P aggregators **must** use user-token for `/prices` |
| Access TTL | Provider returns `expires_in`; cached with a 10% / 5-min buffer (`srs_roof_hub.js:173`) | 30 minutes |
| Refresh model | Re-mint via client-creds on every expiry — no refresh token | Refresh token lasts **forever if used within 30 days**; expires after 30 days idle |
| Reconnect signalling | `_markReconnectRequired` flips `CONNECTION_STATUS` + notifies platform (`srs_roof_hub.js:26`) | Same shape works, but the trigger is a 30-day idle window — needs a per-tenant keep-alive cron |
| Doc / code | `srs_roof_hub.js:134` | `/authorization-methods/` |

**Verdict:** ABC is harder to operate (idle expiry) but more secure (per-tenant tokens, scoped consent). Adapter already implements the refresh-token grant in Phase 1; the keep-alive cron is the only Phase 2 add-on.

### 3.2 Catalog import

| | SRS | ABC |
|---|---|---|
| Endpoint | `GET /products/v2/catalog` (full catalog stream) + `GET /branches/v2/activeBranchProducts/{branch}` for branch-bound | `GET /api/product/v1/items` (paginated, `embed=branches,variations`) |
| Delta sync | Implicit — orchestrator re-streams and dedupes | Explicit `sinceLastModifiedDateTime` — **hard 7-day cap** beyond which a full pull is mandatory |
| Catalog driver | Order-template-driven (`getOrderTemplates` → product IDs → catalog stream) | Items-first; templates are independent (bill-to scoped via `/orders/templates`) |
| Page size | Streamed (`stream-json`) | ≤ 1000 items/page |
| Inactive items | Filtered server-side | **Client-side filter required** (delta returns inactives) |
| Doc / code | `srs_roof_hub.js:676` | `/get-all-items/` |

**Verdict:** ABC catalog is simpler (one endpoint, embeddable variants) but requires a hybrid cron: delta on each run + scheduled full pull every < 7 days. The current SRS Bull worker is template-shaped and won't fit ABC — Phase 2 needs a catalog-first ingestion path.

### 3.3 Pricing

| | SRS | ABC |
|---|---|---|
| List / anonymous price | Yes — `getProductPriceDetailsMaster` returns cost without customer context (`srs_roof_hub.js:730`) | **None.** All pricing requires `shipToNumber` + `branchNumber` |
| Deep / variant pricing | Yes — `getProductPriceDetailsDeep` expands option × UOM × vendor SKU (`srs_roof_hub.js:820`) | Same endpoint as on-demand; use `purpose=quoting` |
| On-demand PO pricing | `POST /products/v2/price` — keys by product+option+UOM | `POST /api/pricing/v2/prices` — keys by `itemNumber`+`uom` |
| Batch cap | None documented (orchestrator chunks at 50 for parity) | **50 lines/request**, hard |
| `$0` semantics | Treated as "no price" — `success:false` | Same — treat as "no branch price configured" |
| Doc / code | `srs_roof_hub.js:932`, `/products/v2/price` | `/price-items/` |

**Verdict:** ABC is a regression on list/anonymous pricing — Zuper catalog rows cannot carry a non-customer cost. Stays stubbed forever; this isn't a Phase-2 gap, it's an API limitation.

### 3.4 Order submission

| | SRS | ABC |
|---|---|---|
| HTTP semantics | `POST /orders/v2/Submit` → **200 + `orderID`** (ORDER) or **201 + `queueID`** (QUEUE) | `POST /api/order/v2/orders` → **202 + batch envelope** always; per-order `confirmationNumber` may or may not be present |
| Identifier semantics | `orderID` is the permanent ref; `queueID` is replaced via webhook | `batchId` is permanent; `confirmationNumber` is the permanent ref once present |
| Line cap | None enforced by API; orchestrator validates | **99 lines/order** (orchestrator must auto-split for larger POs — deferred to Phase 2) |
| Per-line price | Sent in payload | Sent in payload — **caching forbidden**; must re-price immediately before submit |
| Idempotency | `transaction_id` echoed back (`srs_roof_hub.js:1156`) | `requestId` field on payload; ABC docs claim idempotency but behavior under retries is unstated |
| Delivery method gate | Whitelist (JOB_ADDRESS, PICKUP) (`srs_roof_hub.js:1124`) | `deliveryService` free-form per-branch (`DELIVERY` / `PICKUP` are common) — needs branch capability fetch |
| Doc / code | `srs_roof_hub.js:1034` | `/place-orders/` |

**Verdict:** ABC submit is always-async — every adapter response is morally a QUEUE outcome until either the webhook fires or `GET /orders/{n}` is polled. Phase 1 adapter already maps this correctly. Auto-split at 99 is the only outstanding gap.

### 3.5 Webhooks

| | SRS | ABC |
|---|---|---|
| Event types | OU (order update), DU (delivery update), IU (invoice update), OC (order cancel) | `ORDER_UPDATE` (covers order + delivery + cancel + returns + pickup), `ORDER_INVOICED` |
| Accept/reject | Distinct events (OU statuses) | **No explicit accept/reject** — infer ACCEPTED from `Scheduled`/`In Progress`, REJECTED from `Canceled` without prior shipment |
| Delivery states | 9 — SCHEDULED, IN_TRANSIT, OUT_FOR_DELIVERY, ARRIVED, PARTIALLY_DELIVERED, DELIVERED, DELAYED, CANCELLED, UNKNOWN | 3 — `Scheduled`, `Attempted`, `Delivered` (+ pickup variants). Coarser; `Attempted` → DELAYED, no IN_TRANSIT / OUT_FOR_DELIVERY |
| Subscription mgmt | Static / manual | **API-managed CRUD** (`POST/GET/PATCH/DELETE /api/notification/v2/webhooks`) — cap **5 per app**, shared-secret in `Authorization` header (no HMAC) |
| Invoice payload | Pointer-only — must follow up with PDF fetch | **Full invoice rows + totals** inline |
| Returns / pickup lifecycle | Not modeled | First-class via `ORDER_UPDATE` (Pickup Requested → Processed, In Progress → Picked Up) |
| Idempotency | Memcache-backed dedup (`webhooks.js:claimEventId`) | Same dedup pattern applies — ABC payloads carry unique `notificationId` |
| Doc / code | `srs_roof_hub.js:1452`, `services/process_webhook.js` | `/order-update-event/`, `/order-invoiced-event/`, `/register-webhook/` |

**Verdict:** ABC's webhook model is *operationally* nicer (auto-subscribe, richer invoice) but *semantically* poorer for delivery (3 states vs 9). The `DELIVERY_STATUS_TYPE` mapping for ABC will collapse several Zuper states.

### 3.6 Documents & receive

| | SRS | ABC |
|---|---|---|
| Invoice PDF | `GET /orders/v2/{invoiceNumber}` — direct stream (`srs_roof_hub.js:1294`) | `GET /invoice/v1/invoices/pdf/{invoiceId}` — `application/pdf` body |
| Invoice metadata | Embedded in webhook | `GET /invoices/id/{n}` + `/history/{billToAccount}` (extra) |
| Proof of delivery PDF | `GET /orders/v2/{n}/pod` (`srs_roof_hub.js:1402`) | **No endpoint.** Closest is `shipments[].deliveryHistory[]` on `GET /orders/{n}` — render as timeline, no downloadable file |
| Shipped qty per line | `GET` per-order shipped quantities (`srs_roof_hub.js:1354`) returns `shipped_qty` per line | `GET /api/order/v2/orders/{n}` exposes `shipments[].lines[].orderedQty` only — **no separate shippedQty**; must reconcile against the original PO |
| Retry classifier | `isRetryablePdfFailure` — fail on 4XX, retry on 5XX | Same logic should apply |
| Doc / code | `srs_roof_hub.js:1294,1402,1354` | `/get-invoice-pdf/`, `/get-orders/` |

**Verdict:** ABC matches SRS on invoice but cedes ground on POD (no PDF) and per-line receive (no `shippedQty` field). Phase 2 needs (a) timeline view for POD, (b) line-level diff logic for receive.

### 3.7 Vendor / branch / ship-to

| | SRS | ABC |
|---|---|---|
| List all branches | `GET /branches/v2/branchLocations` — flat list | **No "all branches" call** — filter by geo (lat/long/distance) or state. Onboarding needs a state-sweep |
| Branch detail | Implicit in branch list | `GET /api/location/v1/branches/{branchNumber}` — hours, manager, geo |
| Ship-to lookup | `GET /branches/v2/customerBranchLocations/{customer_code}` — by branch_code(s) or geo coords | `GET /api/account/v1/shiptos/{shipToNumber}` — single ship-to with associated branches |
| Account search | `GET /customers/validate` (validation, not search) | `POST /api/account/v1/search/accounts` — returns sold-to / bill-to / ship-to in one call (≤ 2 ANDed filters) |
| Hierarchy model | Flat: `customer_code` → branches | **Three-tier**: sold-to → bill-to → ship-to (+ contacts endpoint) |
| Doc / code | `srs_roof_hub.js:524,464,448` | `/search-branches/`, `/get-branch/`, `/get-ship-to/`, `/search-accounts/` |

**Verdict:** ABC's hierarchy is richer (sold-to/bill-to/ship-to vs flat customer_code) and requires schema work on `customer_data`. Onboarding flow needs a state-sweep step to populate the branch list — SRS' one-shot list call doesn't exist on ABC.

### 3.8 Templates / reorder UX

| | SRS | ABC |
|---|---|---|
| Order templates | `GET /customers/v2/orderTemplates/{customer_code}` — customer-scoped (`srs_roof_hub.js:358`) | `GET /api/order/v2/orders/templates?accountNumber=` (+ `…/{id}`) — bill-to scoped |

| Frequently bought | Not exposed | `GET /api/product/v1/items/{billToNumber}/frequents` — 180-day window |
| Favorites | Not exposed | `GET / PUT /api/product/v1/items/{billToNumber}/favorites` — writable |
| Doc / code | `srs_roof_hub.js:358` | `/get-order-templates/`, `/get-recent-items/`, `/get-frequent-items/`, `/get-favorite-items/`, `/add-favorite-item/` |

**Verdict:** Pure upside on ABC. Phase 3 surface — straight read-through endpoints with no orchestration cost.

## 4. Where ABC is a *better* implementation than SRS

| Area | SRS today | ABC upgrade | How to land it |
|---|---|---|---|
| Account model | Flat `customer_code` | Three-tier sold-to / bill-to / ship-to (+ contacts) | Extend `customer_data` schema; default to bill-to for templates and ship-to for orders. |
| Webhook subscription | Static, manual setup | `POST /notification/v2/webhooks` API-managed (5/app, shared-secret) | Add an onboarding step that registers/rotates webhook URLs; persist secret on provider doc. |

| Product variants | `productVariants[]` flat | `embed=variations,familyItems` returns family + sizes inline | Replace SRS-style option flattening with ABC's hierarchy; cleaner variant UI. |
| Order traceability | Webhook-only | Webhook **+** `GET /orders/{n}` polling fallback | Add a "Refresh from supplier" action on the PO; calls Get Order and reconciles. |
| Returns flow | Not modeled | First-class via `ORDER_UPDATE` Pickup Requested → Processed | New PO sub-state machine for credit-memos. Phase 3. |

## 5. Where ABC is *worse* than SRS (must design around)

- **No anonymous list price** — pricing is always shipTo+branch scoped. Catalog rows can't carry a baseline cost. → keep `getProductPriceDetailsMaster` stubbed; never persist a non-customer price.
- **No POD PDF** — only structured delivery events. → render a timeline instead of providing a downloadable PDF.
- **No explicit accept/reject event** — must infer from `ORDER_UPDATE` transitions.
- **No `IN_TRANSIT` / `OUT_FOR_DELIVERY`** — three-state delivery only (`Scheduled` / `Attempted` / `Delivered`). Either widen `DELIVERY_STATUS_TYPE` mapping or accept a coarser timeline for ABC POs.
- **No `shippedQty` distinct from `orderedQty`** — reconcile against the original PO to compute partial receives.
- **7-day max delta on catalog** — must alternate delta + full pulls in the cron.
- **Refresh token dies after 30 days idle** — needs a per-tenant keep-alive job (out-of-band from the 30-min access-token refresh).
- **Async-only order submit (202)** — every `submitPurchaseOrder` is effectively a `QUEUE` outcome until the webhook (or `GET /orders/{n}` poll) lands the `confirmationNumber`.

## 6. Phase suggestions (informational, not binding)

- **Phase 1 (shipped):** catalog (on-demand), pricing, order submit.
- **Phase 2:** Notification API subscription mgmt, `ORDER_UPDATE` + `ORDER_INVOICED` webhook parsing, invoice PDF download, refresh-token keep-alive, catalog-first cron path that doesn't require order templates, 99-line auto-split on submit.
- **Phase 3:** account-hierarchy migration, returns/pickup lifecycle, reorder UX (recents/frequents/favorites), product hierarchy + family variants, order-refresh polling fallback.
