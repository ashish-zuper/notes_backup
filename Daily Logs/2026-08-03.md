## Dev log

### API-5217 — ABC branch availability from stored data, family-grained template products

*Repo:* `master_service` · *Branch:* `API-5217` · *Ticket:* [API-5217 — ABC family grouping — master_service (adapter, worker, template import, listing)](https://linear.app/zuperinc/issue/API-5217/abc-family-grouping-master-service-adapter-worker-template) · *Commits:* `a3c9efe51`

- ABC branch availability now comes from the per-variant data the nightly importer stores, so this service no longer calls ABC's search-availability API at all. Availability is decided per family member instead of per parent item, so two colours of the same family stop reporting the same answer. SRS is unchanged and keeps its live check.
- The availability check is a provider-agnostic service; suppliers opt in through a capability list. An absent branch list defers to the product-level list so older rows keep working, an empty one means stocked nowhere, and an inactive variant is unavailable regardless.
- Order template imports now find the family row that contains a member's item number, and the created product is titled and keyed by the family — so importing several members of one family gives one product rather than several near-identical ones.
- Purchase-order submission stops trusting the client for supplier item identity. The ordered member is resolved from the master product, and a line that still resolves to a family or lot id is refused rather than sent to ABC. This was ordering the wrong thing: a custom catalogue line submitted a family id as the item number.
- Catalogue listing performance: added the missing index behind the item-number lookup, dropped an unused one, and stopped returning branch lists to clients — they were server-side only and made up most of a listing page's payload.

### API-5218 — ABC importer re-grained to one row per family

*Repo:* `scheduler_service` · *Branch:* `API-5218` · *Ticket:* [API-5218 — ABC family grouping — scheduler_service (importer re-grain, price/availability guards)](https://linear.app/zuperinc/issue/API-5218/abc-family-grouping-scheduler-service-importer-re-grain) · *Commits:* `e2b70de17` `7ac9a758a` `26089cd62` `953f5cf01`

- The nightly ABC import now writes one row per product family, titled with ABC's human-readable family name, instead of one row per item number. A 794-member family previously produced 794 near-identical rows that each repeated the whole roster and its own copy of the raw payload; searching a family name returned a page of apparent duplicates.
- A member's branches, status, units and image only arrive with that member's own record, so each member owns a slot on the family row and the row's availability is recomputed from those slots on every write. That makes the write idempotent and order-independent, so a nightly delta run cannot wipe the availability of members it did not fetch — which the earlier run-scoped design would have done every night except Sunday.
- Requesting the family roster from ABC is now configurable and off by default. It was roughly 72% of each page's payload, and the roster lists far more members than ABC will actually return as items, so variants are built from the members genuinely walked. Turning it back on restores roster-driven behaviour with no code change; the importer detects which shape it received.
- Price-sync no longer skips catalog rows on a field the non-dimensional path never reads. Skipped rows are counted and warned on instead of dropped silently, so a row missing its vendor SKU is now visible rather than just unpriced.
- Option identifiers are keyed on the supplier item number rather than the item description, so a cosmetic rewording by ABC no longer orphans the vendor catalogue rows pointing at them. Dimensional rows carry a single per-length variant instead of colour siblings that could not actually be ordered as those colours.
- Per-variant product images are resolved to S3 by a new post-import pass, covering only variants stocked somewhere.
- Local-run ergonomics: readable console logging and a switch to skip the per-batch S3 catalogue backup, plus a read-only script that rebuilds a family row from ABC live and diffs it against what is stored.

### API-5273 — ABC product category aligned with master_service

*Repo:* `scheduler_service` · *Branch:* `API-5273` · *Ticket:* [API-5273 — Scheduler Service Bug Fix](https://linear.app/zuperinc/issue/API-5273/scheduler-service-bug-fix) · *Commits:* `582b0e5aa`

- The ABC import was reading a product's category from a deeper level of ABC's hierarchy than master_service does, and from a field that carries ABC's numeric code prefix — so one item was stored as "000046  -  Vinyl Siding, Soffit & Accessories" here but "Siding Products" there. Both services now read the same field.
- Not just cosmetic: master_service passes the stored category straight through, but re-derives it for products missing from the nightly clone, and auto-creates a Zuper product category per distinct name — so a single ABC item could end up creating two categories.
- The three places that derived the category now share one helper, so they cannot drift apart again. Checked against a 500-item ABC payload: every item now matches what master_service produces, with none left blank.
- Categories become coarser as a result (17 distinct values down to 5 in that sample), since the shared field is the top-level product group. Stored rows correct themselves on the next import; categories already created under the old names remain and need a separate cleanup.

### API-5202 — ABC import correctness: availability, pricing, status

*Repo:* `master_service` · *Branch:* `API-5202` · *Ticket:* [API-5202 — ABC Testing Findings (3)](https://linear.app/zuperinc/issue/API-5202/abc-testing-findings-3) · *Commits:* `b02875d91` `2ebd12a06`

- Root cause behind two opposite-looking bugs: the supplier-provider facade declared a one-argument `normalizeCatalogProduct`, silently dropping the stored document the importer passed alongside it. No ABC catalog product ever carried per-variant branch availability, so the old permissive check created vendor catalog rows at every branch and a stricter one created none. The catalog product is now built from the stored master document's own fields rather than re-derived from its raw reference copy — which also dropped every family member except one whenever that copy lacked family data.
- Vendor catalog rows are now only created where that specific variant is stocked, decided from data we already hold and checked before pricing, so an item a branch does not carry costs no supplier call.
- An item-level 403 from ABC was failing entire template imports, because the importer called ABC purely to learn a unit of measure it already had stored. That call is not branch-specific for ABC and is now a fallback only.
- Pricing requests were timing out at 30s despite each taking ~10s: the outbound rate limiter paces how often requests start, not how many are in flight, so roughly 90 landed on the supplier at once and it queued the excess. Concurrent pricing requests are now capped.
- A template could report every product as failed after importing them cleanly — the finalize step looked products up by the template's own item number while everything else was keyed by the family's representative. Partial imports were therefore impossible to report. Distinct failure causes (supplier outage, no connected branches, missing unit of measure) no longer all read as "not available at any connected branch".
- Import progress is now visible: templates move to in-progress when queued and reach a terminal state even if the job dies, instead of reading "not started" for the whole run. Duration reduced by resolving product images concurrently, dropping a redundant per-branch delay for ABC, and batching the product back-link writes.
- Purchase orders now fall back to a product's purchase cost rather than its customer-facing sell price when the live supplier price is unavailable — previously the marked-up figure was what got submitted to the supplier.
- Automated CPQ proposals now price line items from the preferred supplier's branch, the same vendor recorded on the quote. With more than one supplier connected the quote could name one vendor and be priced from another.
- Vendor listing and filter APIs no longer restrict results by who created the vendor, so all roles see the full company list. Subcontractor listing, which shares the same handlers, keeps its existing restriction.
