## Dev log

### API-5562 — QXO material order: UAT fixes

*Repo:* `master_service` · *Branch:* `API-5562` · *Ticket:* [API-5562 — Master Service: Setup QXO : Material Order Setup](https://linear.app/zuperinc/issue/API-5562/master-service-setup-qxo-material-order-setup) · *Commits:* `d12370dcd` `75bc954f3`

- Fixed a credential bug that made supplier authentication fail even when a valid refresh token was stored, and then destroyed that token on the way out. Three code paths were affected, including an unattended background job that could have silently disconnected a customer's supplier integration overnight. Only QXO uses refresh-token authentication, so SRS and ABC Supply were never exposed.
- The reference Zuper sends with a supplier order is now a plain UUID. QXO validates the field strictly and rejected the previous format outright; the other suppliers carry it unchanged, and orders placed before this keep working.
- Stopped sending the extended PO number to QXO — the field is not available on the account.

### API-5667 — QXO order polling

*Repo:* `master_service`, `scheduler_service` · *Branch:* `API-5667` · *Ticket:* [API-5667 — Master Service: Create a Polling system for qxo orders](https://linear.app/zuperinc/issue/API-5667/master-service-create-a-polling-system-for-qxo-orders) · *Commits:* `3ec948df2` `96f6dc0`

- Purchase orders sent to QXO now update themselves. QXO publishes no webhooks, so a scheduled job checks each open order every ten minutes and feeds the result into the same pipeline SRS and ABC webhooks already use — status promotion, delivery tracking, line receipt and invoicing all behave identically across suppliers. When QXO eventually adds webhooks, only the event source changes.
- Captured real UAT responses before building, which overturned three assumptions from QXO's API spec: the order reference we send is not echoed back (orders correlate on QXO's own order id instead), shipped quantities per line do exist despite being undocumented, and the documented response envelope was wrong. The spec has now been inaccurate four times on this integration, so payloads get verified against the sandbox before anything is written against them.
- Detection compares against the purchase order's existing status rather than storing a new field, so nothing was added to the schema and no first-run backfill was needed.
- Polling runs on its own queue. The shared supplier queue handles catalog imports and inbound webhooks behind a single concurrency limit, and a burst of order checks there would have delayed SRS and ABC order processing.
- Two gaps remain with QXO: no invoice number is exposed on the order, and there is no cancelled status at all, so a branch-side cancellation currently looks the same as an order that never progresses and is only stopped by an age cutoff.
