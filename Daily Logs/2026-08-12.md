## Dev log

### hotfix/staging_skip_inprocess_workers — staging worker isolation

*Repo:* `master_service` · *Branch:* `hotfix/staging_skip_inprocess_workers` · *Commits:* `84cdff3a8`

- Staging API pods no longer start background workers in-process. Workers are gated on `DEVELOPMENT_ENV_ID`, which is set in every non-live environment, so staging was loading them inside the API process even though it now runs a dedicated worker service.
- That left staging with two consumers on every Bull queue — API pod and worker pod — and whichever won the race decided how a job was handled. Where the two deployments' images had drifted, a job enqueued by the API could be picked up by a worker with no handler registered for it and fail with `Missing process handler for job type <name>`; a supplier delivery-update webhook failed exactly this way.
- Caveat for follow-up: this makes staging deterministic, not correct. If the staging worker image is older than the API's, supplier jobs will now fail consistently instead of intermittently — the worker instance needs redeploying from the same commit as the API.

### API-5377 — supplier circular dependency

*Repo:* `master_service` · *Branch:* `API-5377` · *Ticket:* [API-5377 — Circular Dependency - Supplier Integrations](https://linear.app/zuperinc/issue/API-5377/circular-dependency-supplier-integrations) · *Commits:* `236f95c69` `deb172827`

- Broke the 14-file require cycle spanning supplier_providers, vendor_management, purchase_order and workers/supplier_provider. It was latent rather than crashing — every cycle-closing edge was a hand-placed lazy require, three of which were added by earlier "fix circular dependency" commits that each relieved one edge and left the loop intact. madge now reports zero cycles across those four areas.
- Dominant cause was mundane: three enqueue sites imported the 789-line worker handler module just to get a queue handle, when its whole export is a passthrough of the queue leaf that five other call sites already use. Repointing those three requires removed 36 of the 38 cycles.
- Related to this morning's staging worker isolation: because live API pods never load ./workers, those lazy requires were registering all 9 supplier Bull processors inside request-serving pods on first use — the same dual-consumer problem, arriving by a different route. This closes it for live too, so consumption is now worker-pods-only. Worth watching queue depth after deploy, since API pods were incidentally absorbing some of that work.
- Remaining cycle was a layering violation: provider adapters persisted their own connection state via the provider service, which constructs the facade that constructs the adapters. Extracted the two state writes the adapters need into a leaf module. The SRS token-refresh path also stopped going through a 300-line update service that was replacing the whole supplier_provider_keys subdocument, which had been dropping customer_data.available_branches on every refresh.
- Review at xhigh flagged two regressions this introduces that are not yet fixed — the new credential write lost the Winston logging the old path had, and it replaces the credentials subdocument where the ABC adapter merges per-field. Also surfaced a serious pre-existing cluster: a transient ABC token-endpoint timeout is treated as an auth failure and nulls a refresh_token ABC cannot re-derive, and nothing ever writes connection_status back to CONNECTED. Both need their own tickets.
