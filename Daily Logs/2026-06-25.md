## Dev log

### staging — S3 migration backlog drain: write-batching attempt (reverted)
*Repo:* `workflow_builder_execution_curator` · *Branch:* `staging` · *Commits:* `13079ff` `327cb5b`

- Attempted to speed up the backlog job that moves large execution/node JSON payloads from MySQL to S3 by (a) batching the per-page DB write-back into grouped upserts and (b) prefetching the next page while the current one uploads.
- Reverted — it ran slower, not faster. Root cause: the batched write used `INSERT … ON DUPLICATE KEY UPDATE`, whose INSERT half omits the NOT-NULL `created_by` column, so MySQL strict mode rejected every batch (error 1364) and silently fell back to the original per-row updates plus a wasted failed insert each page. Upsert is the wrong tool for updating a subset of columns on existing rows.
- Next: correct write speedup via parallelized per-row UPDATEs or a CASE-based bulk UPDATE (pure UPDATE, no INSERT), leaving the already-optimal read query untouched.

### staging — S3 migration node drain: keyset pagination to stop throughput decay
*Repo:* `workflow_builder_execution_curator` · *Branch:* `staging` · *Commits:* `ddfce1b`

- Fixed the gradual slowdown where the node-data S3 migration started fast and decayed over a long backlog run. The drain re-scanned the candidate set from the start on every page, which let an in-memory exclusion list of not-yet-finished parents grow without bound, made each query re-traverse the ever-growing region of just-migrated rows, and left each page scanning more to find fewer migratable rows.
- Reworked it to walk the backlog once, oldest-first, using a `created_at` cursor so each page jumps straight to the next un-migrated rows — per-page cost now stays flat for the whole run. A database-side join on parent status returns only rows that are ready to migrate, so the in-memory exclusion list is gone entirely. The query is pinned to the index that keeps it constant-cost (validated via EXPLAIN: indexed range, no filesort), and reads ids first then fetches the large payloads by primary key so ordering never touches the big columns.
- Added decay diagnostics to the backlog progress Slack report (per-page fetch latency, exclusion-list size, % of fetched rows that were migratable) so any future slowdown and its cause are visible at a glance.
- The workflow-execution drain was intentionally left as-is — it has no parent gating, is ~245× smaller, and finishes before any decay can accumulate.
- Open item to verify in prod: confirm no `s3_migration_needed` node rows have a NULL `created_at` (the cursor would skip them); expected to be none.
