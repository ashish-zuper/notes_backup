## Dev log

### API-6327 — normalized supplier categories
*Repo:* `master_service` · *Branch:* `api-6327-01-catalog-taxonomy-models` · *Ticket:* [API-6327 — Supplier TakeOff: Normalize the mentioned fields across supplies](https://linear.app/zuperinc/issue/API-6327/supplier-takeoff-normalize-the-mentioned-fields-across-supplies) · *Commits:* `99bd1e131`

- Added one category tree for all supplier products: 13 departments and 39 product types. Self-serve filters can now use the same categories for SRS, ABC Supply and QXO.
- Added a mapping from each supplier's own category labels to those categories: 610 labels from prod and staging. A few labels mix product types, so name rules split hip & ridge and starter shingles out of shingle labels, and coil and cap nails out of fastener labels.
- Admins seed both collections with one call that creates or updates rows but never replaces them. The response lists what changed. Admins also get a mapping review list, and companies get a route listing all categories.
- New fields on supplier products for the normalized department, type and brand. They stay empty until the normalization job ships.
- Indexes are created on the cluster, not in code; they're listed in one comment on API-6553.

### API-7166 — custom objects: filter records by a linked record
*Repo:* `master_service` · *Branch:* `api-7166-linked-record-filter` · *Ticket:* [API-7166 — Custom Objects: filter records by a linked record](https://linear.app/zuperinc/issue/API-7166/custom-objects-filter-records-by-a-linked-record) · *Commits:* `8a808d1b0`

- Custom object record lists, filters and counts can now return only the records linked to one record, such as a job's permits. A details page can use this for a card of linked records with the columns the user picks.
- The linked record can be a standard record (job, property, …) or another object's record. The association must be active and visible to the user, and records outside the user's view scope never match.
- The card takes the association key and side straight from the existing link definitions API, so the filter meta needed no change.

### API-7170 — recommended supplier products: staging limit and query fan-out
*Repo:* `master_service` · *Branch:* `api-7170-raise-recommended-products-limit-to-150-on-staging` · *Ticket:* [API-7170 — Raise recommended products limit to 150 on staging for load testing](https://linear.app/zuperinc/issue/API-7170/raise-recommended-products-limit-to-150-on-staging-for-load-testing) · *Commits:* `c4859560a`

- The recommended supplier products endpoint now accepts up to 150 local products per request on staging and development data centres. This lets us load-test it before raising production, which stays at 50. The bulk catalog-map limit is unchanged.
- A request now runs the catalog queries for at most 10 products at a time instead of all at once. Before, a 50-product request held the pod's whole 100-connection Mongo pool, and other requests queued behind it.
- Local benchmark on staging data:
  - responses were identical;
  - one request now uses 20 connections instead of 100;
  - at 150 products, other queries' p95 wait dropped from 0.5–1.2 s to about 25 ms;
  - event-loop stalls dropped from up to 256 ms to under 40 ms;
  - the request itself got slightly faster.
- PR: [#2991](https://github.com/ZuperHQ/master_service/pull/2991).

### API-7167 — custom objects: recover deleted records
*Repo:* `master_service` · *Branch:* `api-7167-recover-deleted-records` · *Ticket:* [API-7167 — Custom Objects: recover deleted records](https://linear.app/zuperinc/issue/API-7167/custom-objects-recover-deleted-records) · *Commits:* `152d19cf0`

- Deleted custom object records can now be listed (last 90 days, with who deleted them and when) and recovered through the same recover API shape other modules use, up to 100 records per call.
- Deleting a record now keeps its links, marked deleted, so recovery brings them back. A link to a record that is still deleted waits until that record is recovered; a link whose other record has meanwhile taken its only allowed link is dropped. Unlinking by hand stays permanent.
- Recovered records count against the object's record limit again, and each one gets an activity entry and a recover webhook event.
