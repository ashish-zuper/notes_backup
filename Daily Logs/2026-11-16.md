### API-6845 — Custom object review changes: indexes and permissions
*Repo:* `master_service` · *Branch:* `api-6845-06-review-changes` · *Ticket:* [API-6845 — Custom Objects: records and links](https://linear.app/zuperinc/issue/API-6845/custom-objects-records-and-links) · *Commits:* `1129fef03`

- The custom object permissions API now returns rights as true/false instead of 1/0.

### API-6845 — Custom object review changes: access gaps and response consistency
*Repo:* `master_service` · *Branch:* `api-6845-06-review-changes` · *Ticket:* [API-6845 — Custom Objects: records and links](https://linear.app/zuperinc/issue/API-6845/custom-objects-records-and-links) · *Commits:* `13f6b5224`

- The custom object permissions list now returns each role's active flag as true/false instead of 1/0.
- Counting a custom object record's notes works; it was always refused before.
- Notes no longer show custom object records the user can't open (no view right, outside their view scope, or the feature off), even when the note is on a Job they can see.
- The settings associations list hides associations with objects the user can't see, and a record's association group with an archived object is not found, matching the record's association list.
- Creating or archiving an association returns the full definition, as updating does; refused custom field changes are titled with the reason instead of "Access Denied"; updates that only send empty settings groups are refused as having nothing to change.

### API-6845 — Custom object review changes: notes format
*Repo:* `master_service` · *Branch:* `api-6845-06-review-changes` · *Ticket:* [API-6845 — Custom Objects: records and links](https://linear.app/zuperinc/issue/API-6845/custom-objects-records-and-links) · *Commits:* `2d486671c`

- Notes now name custom object records the same way they name Jobs or Customers: `co_permit: <record uid>` when creating a note and `filter.co_permit=<record uid>` when listing or counting, so the apps can use one code path for every module.
- Each note returned shows its records under the same keys (`co_permit: { record_uid, record_id, display_name }`); storage, access checks, activity entries and events are unchanged.

### API-7040 — OAuth sign-in for the Zuper CLI and the platform service
*Repo:* `master_service` · *Branch:* `API-7040-cli-platform-oauth` · *Ticket:* [API-7040 — Analysis: OAuth sign-in for the Zuper CLI and the platform service](https://linear.app/zuperinc/issue/API-7040/analysis-oauth-sign-in-for-the-zuper-cli-and-the-platform-service) · *Commits:* `5775905cc` `4811b690e`

- Registered the Zuper CLI as a pre-registered OAuth app. It signs in through the browser with a loopback redirect on any free port, and gets only jobs access from master plus a single `platform:write` scope for the platform service.
- One sign-in can now give separate tokens for master and the platform service. Each configured API can carry its own scope set and a shorter token lifetime. Master refuses platform tokens, and apps not allowed platform access (Claude, ChatGPT, Cursor, company apps) can't get one.
- Code exchange and refresh are now refused when the company is inactive or has OAuth turned off, since the platform service can't check that switch itself.
- Master refuses to start on a misconfigured API entry (missing URL, unknown scope set, or lifetime above the default), so a yml indentation slip can't quietly turn the platform API into one of master's.
- Opened PR #2965, stacked on #2782.
