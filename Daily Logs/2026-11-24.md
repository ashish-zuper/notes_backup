## Dev log

### API-7266 — Custom objects: record PATCH in the generic module format
*Repo:* `master_service` · *Branch:* `api-7266-custom-objects-review-follow-ups-nov-20` · *Ticket:* [API-7266 — Custom Objects: review follow-ups (Nov 20)](https://linear.app/zuperinc/issue/API-7266/custom-objects-review-follow-ups-nov-20) · *Commits:* `714d45f97` `c11c2f3b1`

- After the EM's review, custom object record PATCH now follows the company-wide PATCH format used for jobs: a flat body where custom fields are `internal_key: value` pairs, so grouped fields need no group in the request.
- Keys that can't be applied (unknown, read-only, bad values) are ignored and reported back in `ignored_fields` with a reason, with `status` `success` or `partial_success`, instead of failing the whole request.
- Record list, filter and details take `include_custom_field_internal_object=true`, as jobs and customers do, so the apps can read values by the same keys they PATCH with; fields hidden by field restrictions are left out.
- Pushed to #3056; the PR description and Postman are updated, and the earlier Linear comment's PATCH section is marked deprecated in favour of a new comment with the updated format.
- Follow-up fix found by the unit tests: record reads for users with field restrictions checked the restrictions twice, even when the internal-object map wasn't asked for; the second check now runs only when a record carries the map.

### API-7267 — Custom objects: filter any module by related records
*Repo:* `master_service` · *Branch:* `api-7267-custom-objects-filter-any-module-by-related-records` · *Ticket:* [API-7267 — Custom Objects: filter any module by related records](https://linear.app/zuperinc/issue/API-7267/custom-objects-filter-any-module-by-related-records) · *Commits:* `d31365aef`

- Custom object lists can filter by a related module (`job_uid`, `co_inspection`) instead of one specific association, so the apps no longer need association keys and saved filters survive an association being recreated; association keys still work where one exact association is needed.
- Jobs, quotes, invoices, projects, service contracts, assets and requests filter by custom object records with a `co_<api_key>` rule through the shared filter engine. The rule adds to other conditions rather than replacing them, and each module's filter panel lists the custom objects linked to it that the user can view.
- Customers, organizations and properties take the same filter as a `filter.co_<api_key>` param on their list APIs, since they don't use filter rules.
- Linkable modules come from the existing link-target list and plural names from the custom fields alias map, so neither list is duplicated.
- Affected unit suites (jobs, calendar, analytics, customers, assets, invoices/quotes, custom objects) pass with no new failures; the live API tests haven't been run yet. Pushed; no PR opened yet.
